# Remote control contract v1 — admission boundary

Status: implemented library contract for prompt / cancel / bounded history / durable scoped catalogue / durable existing-grant selection / explicitly permitted durable creation / scoped interaction response / durable saved automation reads and controls, plus scoped catalogue/selection, explicitly permitted native creation/reconciliation and durable output primitives; not an externally deployed API. No real channel or model acceptance is implied. Reserved pairing/mobile operations below are permission requirements, not implemented external methods. Changes require a contract review and additive protocol versioning.

## Ownership and dependencies

`xharness-remote -> xharness-api` only. The gateway never owns an Agent, tool registry, model provider, scheduler or platform poller. The executable composition will attach it to the existing Host and run its supervisor independent of connection lifetimes. The executable now mounts an **opt-in private supervisor**, enabled only by `--remote-control enabled` or `XHARNESS_REMOTE_CONTROL=enabled`, after authoritative startup basics. It is disabled by default and excluded from hosted Prepared/cloud workloads. Saved enabled Telegram accounts now start independent native intake/outbox/scoped-interaction workers using a separate channel credential namespace. An empty/disabled configuration performs no provider HTTP or credential reads. A dedicated desktop-only setup/status/private-scope/revoke/recovery extension and bilingual Settings source are implemented. No QR relay or controller authentication endpoint is mounted. Scoped Telegram approval/question notifications and durable assistant text/status/history-catch-up producers are composed; see remote-control-interactions-v1.md and remote-control-output-v1.md. Explicit paginated history and closed command-result replies are composed through atomic result/outbox markers; see remote-control-command-replies-v1.md. Event-owned bounded outgoing images/files are composed; see remote-control-media-v1.md. The setup extension requires opted-in non-hosted loopback composition with strong desktop authentication and same-origin/Host fencing. Disabled compositions reserve the exact path with closed 404, not generic RPC fallthrough.

`ApiBackend::session_in_workspace`, `ApiBackend::session_events`, `ApiBackend::session_event_page` and `ApiBackend::prompt_receipt` are trusted in-process seams. They are not new members of the public RPC directory. Default backends fail closed. BasicHost rejects mismatched scopes from registered workspace paths and known session/header metadata before cold recovery, then revalidates the hydrated cwd; it queries original durable inbox admissions, not public history text or a bounded message cache. A non-authoritative Host cannot certify a durable prompt receipt.

The executable architecture baseline declares only the gateway's API dependency. Source guards reject a gateway that imports Host/Agent/Core or forwards dynamic RPC/respond/global Host streams.

## Identity, authority and commands

An authenticated channel adapter supplies `Sender(channel, account, user)` and transport conversation metadata. A message body cannot override them. An explicit trusted desktop grant maps that sender to a principal and Host, with BOTH workspace and session allowlists. Groups require a separate explicit conversation binding; a private binding does not authorize a group conversation. Binding generation and principal permission revision are captured at durable intake and checked again at dispatch.

| Operation | Required authority | Host reuse boundary / status |

| Prompt / queue / steer with text or inline media | active principal, matching sender/conversation, current generation, workspace + session | Implemented: `session.prompt` with generated stable RPC id |
| Cancel | same session authority | Implemented: `session.cancel`; ambiguous cancellation never replayed |
| History | same session authority, max 1–500 messages | Implemented: `session.history` with bounded before-sequence pagination and durable Telegram result replies; no global event subscription |
| Workspace/session selection | filtered granted catalogue, never cwd browsing | Implemented narrow catalogue and existing-grant binding selection primitives, plus durable Telegram /sessions pages and /select transition receipts/replies. Mobile selection transport remains pending. Selection itself does not grant or create |
| New session | explicit revision-bound creation policy in a granted registered workspace | Implemented native original-receipt recovery, default-off desktop capabilities and normalized Telegram /new with exact additive revision-transition replies. | Approval/question response | same scope + gateway-minted single-use interaction identity + expiry + exact pending Host request | Implemented closed `answer_interaction`, native pending-instance snapshot/response seams and durable once-only tickets; arbitrary `ClientResponse`/RPC ids are not ingress types |

No controller credential exists in this library yet. Desktop launch tokens must never be passed to it as remote credentials. Pairing/controller credentials and relay authentication still need dedicated cryptographic implementations before any external endpoint is exposed. Implemented interaction handles use native CSPRNGs but are not standalone controller credentials; verified sender and exact principal scope remain mandatory.

## Scoped downlink

`Gateway::subscribe` verifies transport sender/conversation and an exact binding generation. `BasicHost::session_events` hydrates and validates only a registered workspace/session pair, emits its current projection/queue/pending interaction baseline, then filters live session frames. The existing desktop all-session mux is unchanged. Backends without this scoped capability fail closed; the gateway never falls back to all-session or Host-global subscriptions.

The gateway reconstructs typed mux envelopes, verifies session and correlation/method shape, and removes unexpected outer payload fields. Permission revision, binding and native workspace scope are rechecked before each emitted frame and on a 200 ms idle timer (native scope checks have a two-second timeout). Revocation or rebind closes existing streams; it does not cancel accepted Agent work. There are 32 bounded pull subscriptions, no growing per-controller queue, and an 8 MiB serialized frame limit. A lag/error becomes a sanitized `StreamGap` and closes the subscription; consumers must restore bounded authoritative history and resubscribe. No global diagnostics or skipped-frame counts are exposed. A relay event protocol remains unfinished. The Telegram scoped observer now drives an independent forward-page reducer with atomic cursor/state/outbox checkpoints and restart catch-up; see remote-control-output-v1.md. Native account intake, scoped observer and outgoing sender remain separate drained siblings. Explicit history-command and event-owned attachment producers are composed through the same durable outbox.

## Durable lifecycle

```text
verified transport metadata + normalized request
    -> SQLite transaction (dedup key + queued command)
    -> durable intake acknowledgement
    -> session FIFO + principal read fence
    -> current scope/generation/revision check
    -> durable dispatching
    -> existing Host admission/operation
    -> durable completed + RPC result
```

The dedup key hashes version, Host, verified sender, conversation and stable platform/request id. It intentionally excludes current binding/session: redelivery after rebinding cannot create a second task in another session. Changed command or binding for the same identity is a conflict. Intake errors are **not acknowledgements**: transports may advance offsets only after a durable disposition. The trusted `receive` seam journals accepted input or a terminal malformed/unsupported/forbidden rejection and the next cursor atomically. Rejection records retain only identity, payload digest and a closed reason code, not private raw payloads. Capacity/storage/identity-conflict errors do not acknowledge input.

`completed` means the Host returned a result, including a business failure. It does not mean the Agent finished or a platform reply was delivered. They are distinct from the outgoing journal states and the composed native output producer.

Recovery:

- `queued`: safe to dispatch after fresh authorization and Host scope checks.
- `dispatching` prompt: query original durable Host receipt. Matching admission finishes without another Host call; verified absence allows the identical fenced request; unavailable/conflicting receipt becomes `uncertain`.
- Selection commits binding, completed original delivery, transition reply proof and any proven projection continuation in one FULL transaction; no Dispatching mutation or original-scope rewrite. See remote-control-selection-commands-v1.md.
- Creation reserves native identity with Dispatching atomically, completes an exact additive grant/result/proof transaction, and reconciles Uncertain only from the original durable receipt. Manual observed-accepted cannot certify creation. The supervisor performs bounded receipt-only recovery. See remote-control-creation-commands-v1.md.
- `dispatching` history/catalogue: side-effect-free retry after authorization; committed results are returned without another native read.
- `dispatching` cancel: `uncertain`, never replay against a later turn.
- Permission/binding changed while queued: terminal `rejected`.
- Permission/binding changed after a dispatch crash: `uncertain`, not a false rejected claim.
- `uncertain`: blocks later commands in that same Host session. Independent sessions remain eligible. Trusted `resolve_uncertain` commits a terminal observation and append-only evidence-digest audit atomically. Resolutions never replay the old request. `AbandonWithoutReplay` is explicitly `abandoned`, not a false rejected/not-applied claim. Metadata-only trusted desktop recovery UI is implemented with exact immutable identity and atomic interaction sealing; see remote-control-inbox-recovery-v1.md. Do not delete uncertainty to force progress.

No exactly-once external-tool side-effect guarantee is made. No outgoing-provider send is retried by rerunning the Agent.

## Durable outgoing replies (trusted composition, not controller commands)

`enqueue_replies` journals a bounded batch of semantic reply plans in one transaction. A stable semantic identity is combined with Host, verified sender and conversation for deduplication. Same identity with changed content, permission revision or binding is a conflict, not an edit or second send. All parts succeed together or roll back, including capacity and duplicate-conflict failures. Queueing checks current principal/binding and genuine Host scope; scope checks time out after two seconds. This method is private trusted formatter/service composition, not an unauthenticated prompt/reply forwarding endpoint.

```text
scoped projection/formatter -> pending (durable whole batch)
    -> recipient FIFO + account/principal fences + current Host scope
    -> sending (durable attempt, account generation, known edit receipt)
    -> delivered / rejected / uncertain
```

`ReplyTransport` can only perform its own provider effect; it has no Agent/Host dispatch method. The sender holds account/principal fences across a bounded 60-second provider call. A revoke or account takeover linearizes after that call; recipient locks are acquired before account locks so a takeover is not delayed by queued duplicate callers. Stale scope rejects a pending reply without a provider effect. Unavailable Host scope leaves the record pending and returns an explicit service error. A pre-cancelled worker does not claim sending; shutdown during a send is uncertain.

Only an authoritative NOT-SENT rate-limit response queues a retry, with persisted 1–3600 second backoff and at most 32 send attempts. Disconnect, timeout, server failure, malformed/mismatched receipt, or interrupted sending after process death never auto-replays. On restart the new account generation marks the prior sending record uncertain. Uncertainty blocks later replies to that recipient, not other recipients or the inbox/Agent supervisor. A sender restarted within the same account generation must acquire a fresh generation to recover its interrupted sending records; it must not reset them to pending. The account sender is serial with a bounded effect; its independent worker cancellation is not an Agent cancellation.

An edit references a previously **delivered outbox record** in the exact sender/principal/revision/binding scope, never a raw controller-supplied platform message id. Only that record's persisted provider receipt becomes the edit target, and the returned receipt must match. `resolve_reply` is trusted desktop recovery: observed-delivered receipt, verified-not-sent, or abandon-without-replay. The state change and append-only evidence-digest audit commit atomically, exact repeats are idempotent, changed review identity conflicts, and none triggers a resend. `reply_audit` is a bounded trusted read; the dedicated desktop outgoing review implements this trusted recovery.

Limits: 64 plans per atomic batch, 128 KiB text per plan, 8 MiB serialized batch, 16 keyboard rows/64 buttons with bounded opaque callback values, 1024 outstanding outgoing records and 100000 retained outgoing identities. Outstanding uncertainty counts toward backpressure; records are not silently discarded. Text/buttons and a separate optional event-owned attachment reference are implemented reply bodies. Media captions are bounded to 1024 UTF-16 units, with no keyboard/edit, and decoded bytes to 4 MiB. General assistant/history catch-up and explicit history replies are composed; bounded event-owned media is composed and real-account acceptance remains required. Native account-worker composition and scoped interaction handles/notifications are implemented; fixture acceptance does not certify an actual account.

## Fencing, limits and durability

One process holds an exclusive consumer lock for the private Host journal. After channel workers stop and the admission supervisor drains, trusted `Gateway::close` closes the transaction gate under its mutex and explicitly releases ownership. Queued blocking jobs/old administrative handles cannot write after close, and dropping an old handle cannot unlock a new consumer. This avoids relying on asynchronous task-capture destruction timing to reopen the service. Account acquisition increments a durable generation and preserves its receive cursor; late callbacks/checkpoints from an old adapter fail with `StaleLease`. Configured production accounts require the exact enabled settings revision when acquiring a lease. A slow old credential/getMe lookup cannot revive an account after disable/rotation; unconfigured legacy composition cannot acquire a configured account. Cursor updates use compare-and-swap; duplicate acknowledgements never move a cursor backward. SQLite WAL + `synchronous=FULL` commit precedes receipt/offset acknowledgement. DB ownership binds to one Host identity; reopening it with another Host fails. Unsupported schema versions and symlink journal files fail closed. Unix directories/files use 0700/0600; native Windows ACL acceptance remains pending.

Per-session Tokio gates enforce FIFO across bindings and principals. Principal read/write fences make revoke and permission updates linearize against in-flight admission, without serializing independent session admissions. A graceful supervisor shutdown waits for accepted in-flight calls; fatal worker errors also drain other workers. No controller-connection cancellation token reaches Host calls. Process death is recovered from the journal.

Limits: 8 MiB serialized intake and 8 MiB serialized Host result (oversized results become bounded errors, not silent truncation), 128 content parts, 128 KiB per text part, 6 MiB encoded per attachment, 1–500 history messages, 1024 outstanding records, 100000 retained dedup identities, 32 worker slots. Capacity exhaustion is explicit backpressure, not acknowledgement. v1 never silently drops old dedup identities; maintenance/compaction will need an explicit retention contract. Typed content permits inline text/image/file data only; Host validates content and stores attachments through the existing ingestion path. Local paths, controller-provided reference ids and download URLs are not content variants.

## Native account configuration and credential composition

`AccountSettings` is trusted desktop state, not remote ingress: channel/account, enabled flag, monotonic revision and bounded role-to-native-reference map. Secret/token/endpoint fields are not part of its closed schema. Settings CAS, receive-cursor preservation and old-connection generation invalidation commit atomically under the bounded provider account fence. Exact duplicate settings do not invalidate a current connection again. Sixteen accounts and eight references per account are bounded; configured production leases require the exact enabled revision. Disable/rotation stops new input/output while already accepted Host work remains durable and continues under its existing policy.

The opt-in executable starts `AccountManager` independently of admission. It observes saved settings, loads only a Telegram `bot_token` reference from the dedicated native channel store, verifies official identity/webhook state and starts the existing `Intake`/outbox workers. The current production connector supports Telegram; Feishu/Lark/iLink/relay are not claimed as implemented. Connection states distinguish disabled, starting, verified online, stopped and closed-code failure; online does not mean a model completed or an output reached the recipient. Credential/provider conflicts and worker failures are not hot-retried every poll: explicit revision change/restart is required. Independent accounts connect concurrently. Manager failure and panicked account tasks are observable rather than stale online states.

Channel keyring service is `com.xlang.xharness.channels.<state-dir digest>`, separate from model credential RPCs' existing `models` namespace. No `.env`, environment token, credential file or plaintext fallback is used. Setup generates a fresh opaque reference, journals inactive cleanup metadata **before** writing the native secret, then commits settings; cancellation/crash cannot orphan an untracked key. Failed writes/setup leave a bounded durable cleanup queue. Rotation retires unused old references; references still used by another saved account cannot be deleted. Cleanup first tombstones the reference transactionally, preventing reactivation between scope check and native deletion; tombstones remain after success and cannot be reused. Native operations have five-second deadlines; ambiguous/incomplete cleanup remains retryable and observable, not a false failed-config or successful-delete claim. Cleanup is trusted local administration, not Bot control. There are at most 1024 pending retired references and 100000 retained tombstones, without silent compaction.

On stop, every account is cancelled before all handles are drained. The genuine Telegram connection explicitly awaits all three workers after a sibling failure; interrupted provider sending persists uncertainty before journal close. No account cancellation token is passed to Agent admission. The journal is closed even on supervisor errors. Desktop setup/status/outbox-recovery and scoped interaction producers are implemented. Exact-identity inbox-interaction uncertainty recovery UI is implemented without replay or unsealing. Actual system-keychain acceptance on each OS is pending; memory-key fixtures do not prove native store access.

## Remote build evidence hygiene

Rust is compiled only on the authorized remote node. Sync current uncommitted source with exclusions for Git/build/node_modules, `.env*`, credentials, cookies and private keys. Use checksum synchronization without preserving local mtimes (`rsync -azc --no-times`): a file edited locally while an older remote build runs can otherwise arrive with a timestamp earlier than that older artifact and be incorrectly treated as unchanged by Cargo. Hold a named exclusive build lock, verify no active cargo/rustc before syncing, compare source hashes and confirm new test identities actually execute. Never sync Rust source into a live build. If stale metadata/artifacts are proven, invalidate the affected remote package caches and re-run; a pass from an old binary is not evidence for the current source. Local `cargo fmt` is non-compiling and remains allowed.

## Dedicated desktop administration (2026-10-10)

POST /api/remote-control/manage is a feature-owned native extension, not public RPC or a Bot/controller command. Strong desktop launch-token/HttpOnly-cookie authentication, exact listener Host/port, same-origin Origin/Fetch-Site, custom header, closed actions without Debug/Serialize and a 64 KiB body limit protect setup. No raw request recorder is involved. Installed after startup, cleared before shutdown and excluded from hosted capability composition. Disabled compositions reserve the path with no-store 404 not_enabled to avoid credential-shaped dynamic-RPC input.

Status never returns secrets/references. Private grants require a genuine registered bound workspace/session and private conversation, atomically commit principal/binding, enforce CAS and reject duplicate active sender authority. The closed grant_scopes action atomically configures complete workspace/session allowlists and an explicit, default-off revision-bound creation policy, with independent exact policy-generation CAS. Native paginated metadata certifies every selected scope and the bound pair before commit; no truncated scope list is adopted. The legacy single-session action does not reactivate a stale creation policy. See remote-control-grants-v1.md. Listing explicitly pages 25 entries; excess bindings return capacity rather than hidden scope loss. Recovery metadata omits output bodies and fixes reviewer identity server-side, without replay/resend. Settings is local, lazy, bilingual, monochrome, receipt-validated and non-retrying; unsupported channels are explicit. CLI opt-in is still necessary: persistent global activation, groups, controller pairing/mobile catalogue/creation transport and actual-platform/model/native-OS acceptance remain future gates. Scoped interaction tickets and Telegram notifications are now implemented; see remote-control-interactions-v1.md. See the source-hashed administration checkpoint for exact verification limits.

## Scoped controller catalogue and session selection

`controller_catalogue` authenticates the exact principal, channel/account/sender, conversation and binding generation, checks the current native binding, then calls only the fail-closed `ApiBackend::scoped_catalogue` seam. The native read includes registered allowed workspace names and a sorted 25-entry session page filtered by both allowlists and workspace ownership. Archived/deleted sessions are omitted. No filesystem path field, broad desktop RPC, bulk session hydration or title/model request is exposed. Cold headers may have unknown titles and explicitly restoring metadata. The ordinary bound-session scope preflight retains its existing hydration behavior. See remote-control-catalogue-v1.md.

`controller_select` chooses only an already granted pair present in a native unarchived catalogue cut. A principal-owned write fence, exact current binding and FULL SQL commit protect the generation update, including caller cancellation. Same-current-target is a no-op; changed scope advances generation once and invalidates old subscriptions/tickets/outgoing authority. It cannot create a session, expand permissions or select cwd. No external catalogue/selection endpoint is mounted. The private Telegram /sessions command now uses normalized durable Catalogue ingress and the exact scoped seam; durable Telegram /select and /new are also composed through separate exact transition proofs. Mobile endpoints remain unexposed.
