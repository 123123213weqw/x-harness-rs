# Scoped remote interactions v1

Implemented trusted native/gateway/Telegram composition, not a public generic RPC or a certified real account. Additive to remote-control-contract-v1.md. Full product/Goal acceptance remains unfinished.

## Authority and native ownership

An interaction handle is 24 CSPRNG bytes encoded as 48 lowercase hex characters. Possessing it does not grant controller authority. Native Host, verified platform sender/account/conversation, principal revision, registered workspace/session, binding generation and the exact pending instance must all match. Telegram callback data cannot choose a principal, workspace, session, raw RPC result or filesystem path.

ApiBackend::session_interaction and answer_session_interaction are narrow trusted in-process seams, not public RPC-directory methods. Default implementations fail closed. BasicHost checks genuine registered workspace scope and the pending request's session before capturing or responding. The closed answers are approval allowed/rejected, complete question answers, or question cancellation. Existing native tool/AI-review policy stays unchanged. Manual responses are unavailable while AI review or an approval decision is in progress.

Each native pending instance has a lazy CSPRNG nonce, shared only by clones of that same instance. Reusing RPC/approval/tool-call strings or restoring a question creates a different nonce. The response requires exact nonce plus typed frame equality. Native approval DecisionClaim and driver acknowledgement remain authoritative; stale clones cannot send to a replacement pending instance. Question gates validate all answers and native durable pending state before append/sink/continuation effects. Transient deferral/deadline fields are not question identity. Native option selection uses the existing option label, not an invented option ID.

Native receipts distinguish accepted, definitely stale before effect, definitely invalid before effect and uncertain after a possible effect. A lost driver acknowledgement or question append followed by a failed continuation must be uncertain, never a false successful/definite-non-effect response. The desktop's existing respond path is not exposed through the gateway.

## Durable tickets and no replay

The closed command is answer_interaction with a gateway-issued token and a closed typed answer. Admission uses the existing stable platform/request identity and session FIFO. Private SQLite records retain the token/snapshot; their lookup key is hashed, but the journal is not encryption at rest. TicketToken and structured callback/button Debug fields redact the raw handle. User-visible custom-answer instructions necessarily contain the scoped handle; do not log message bodies as credentials or claim all arbitrary text Debug fields are secret-free.

Tickets capture exact scope/revision/native instance and a fixed 1–600 second wall-clock deadline. Repeated projection reuses an identical current issued handle without extending its expiry. The durable observed clock watermark fails closed on a rollback below a previously committed observation. Observed expiry commits terminal expired state before returning forbidden. Clock correctness still depends on the host clock; this is not a trusted hardware clock or a guarantee about unobserved offline clock changes.

The FULL claim transaction commits ticket dispatching, a global native-instance consumption fence and inbox dispatching before calling the narrow native answer. Multiple authorized controllers cannot each consume the same pending instance. Completion atomically stores the native receipt, ticket/fence state and inbox result. Native lookup has a two-second deadline; response has a 30-second deadline. Expiry is checked at claim linearization, not promised to cancel a native decision already claimed.

A crash, cancellation, timeout or missing acknowledgement after claim is uncertain and never automatically answered again. Restarted dispatching records terminalize uncertain without calling Host. Definite invalid-before-effect results allow only a new manual handle; the same click/handle cannot be recycled. Trusted inbox uncertainty resolution does not reopen the old native-instance fence. Existing manual recovery APIs remain audited and non-replaying; an inbox-interaction uncertainty UI is still required.

## Telegram production composition

Verified TelegramConnection now has three independent siblings: durable Intake, scoped interaction observer and durable provider sender. Any sibling failure cancels the shared lifetime, then all siblings are awaited before journal close. No observer or account token cancels Agent-owned work.

The trusted account observer catalog validates a current lease and current authorized routes, rejects ambiguous sender/conversation bindings and fails explicitly beyond 32 subscriptions rather than silently truncating. Each observer uses only Gateway::subscribe, not a global Host/mux fallback. Old binding-generation workers drain before replacements acquire permits. Interrupted pull queries never retain a principal reader across SQL awaits: a per-principal write epoch and a non-awaiting read/epoch check reject cached pre-write authorization. Owned authority write guards move into the blocking SQL job and survive caller cancellation through commit or rollback; the epoch advances before releasing that writer. A racing write becomes a sanitized gap; reconnect must authorize the current scope. Rebind/revoke during notification commit retires only that scope worker, rather than stopping unrelated subscriptions. The output commit revalidates account lease in the same transaction, including caller-cancelled blocking transactions.

Native pending approvals/questions produce plain-text notifications, lossless UTF-16-bounded chunks and buttons on the final chunk. Stable token-derived plan identities feed the existing atomic outbox, so scoped reconnect, sanitized gaps and account/service restart do not resend an already journaled notification. The observer restores actual pending interactions from scoped native baselines; this does not implement general assistant history/event-cursor recovery. Pending handles are checked every 30 seconds; still-pending expired handles can be replaced by a new notification, never an automatic decision. A global uncertain/consumed native-instance fence prevents renewal/re-answer after ambiguity.

Callback grammar: a:<handle> approve once, r:<handle> reject, c:<handle> cancel question, q:<handle>:<canonical 0-based index> select an option for exactly one question. The index is mapped to the stored native question ID/label after verified sender/scope lookup; forged/out-of-range/noncanonical choices fail before native effect. Multiple questions/custom text require the complete closed /answer <handle> <JSON array> command. No partial multi-question button response is synthesized and attached media is not silently dropped.

Callback acknowledgement occurs only after durable receive/disposition/cursor commit. Received is an intake receipt, not Approved or native completion. Informational ACK failure never rolls back the cursor or replays the decision. Provider sends remain owned by the independent outbox: only definite not-sent rate limits retry, unknown sends remain uncertain and do not rerun the native response or Agent.

## Limits and remaining work

Closed canonical snapshots are at most 128 KiB; answers and question shapes have explicit count/text limits. Ticket retention is bounded at 100000 records without silent deletion. Each observer holds at most 32 pending IDs; all subscriptions share the gateway's existing 32-slot budget. Plain text, keyboard and atomic-batch bounds remain the outbox/provider contract.

Terminal-button visual removal, stale queued-notification presentation, localized Bot copy and complete assistant/history/tool/media projection are not certified by this checkpoint. Old visible buttons still fail closed at current native/ticket authorization. Groups, controller catalogue/selection transport and session create, mobile relay/QR, iLink, Feishu/separate Lark, schedules, persistent global Settings activation, real accounts/models/keyrings, native OS runtime acceptance and executed CI remain completion gates. HTTP/SQLite/native-driver and actual disposable service fixtures are reported separately from real platform/model trials.
