## 证据与定位

原始 CI 在 Linux WebKit 的单次 `-100000px` 轮后未触发分页。独立检查不能简单将其
归因于超大滚轮：普通 `-600px`、`-180px` 也有首轮失效；纯 HTML 原生滚轮对照正常。
丢失轮中事件送达且未被 preventDefault，几何变化只有 `top = height - viewport` 的底部钳位。

隔离生产图 A/B 使用同一首次底部稳定条件、同一普通单次 `-600px` 输入，不点击加载历史，
不通过程序性 scrollTop 制造上滚。不同批次受 CPU/时序影响，以下是功能对照，不是性能基准：

| 诊断变体 | Linux 观察 | 处理 |
|---|---|---|
| 原始生产实现 | 两个批次分别 1/3、0/3 真正离底 | 保留失败日志 |
| 仅去掉即时浮动按钮状态更新 | 0/3 离底 | 不提交 |
| 去掉窗口测高补偿 | 两批分别 0/3、1/3 离底 | 不提交 |
| 避免重复到底部写入 | 0/3 离底 | 不提交 |
| 首个滚轮后推迟窗口计划 300ms | 0/5 离底 | 不提交；延时不是修复 |
| 完全关闭窗口化 | 两批各 3/3 离底 | 只用于定位，禁止作为交付 |
| 保留窗口化，RAF 中同步提交实际行计划 | 5/5 离底，均保持 600px 阅读间隙 | 据此实现最终候选 |

新增同帧收据测试在旧生产源码上明确失败：近屏行 0～5 的控制器 RAF 已执行，但其实际 DOM
全部仍为 `mounted=false`。候选实现同断言通过。这证明了控制器状态与 DOM 提交边界不一致；
后续高度收缩与首轮钳位由生产图复现，未声称已经单独剖析 WebKit 内部滚动算法。
第一次旧源码测试因为外部 node_modules 符号链接被构建 guard 拒绝，属于环境准备失败，
改用隔离实体依赖后才取得以上有效负对照；不把准备失败计为产品复现。
