# 历史存储的无损渐进迁移

## 目标与边界

本机大量历史数据主要来自旧 JSONL 中重复的请求审计，以及新版本 `request-audit/` 的按内容寻址对象。**不允许用删除历史或缩短上下文冒充存储优化**；普通历史、按需请求审计、会话恢复及未来追加必须保持可用。

迁移应分成独立、可验证的阶段，不在一次启动中重写全部文件，也不以升级失败阻止用户打开会话。

## 第一阶段：启动只枚举头部（本次）

- `Store::scan_startup_candidates` 为可选的启动候选接口。普通 Store 默认调用原来的完整扫描；JSONL Store 只读取并校验不可变的首行 Header。
- Host **逐个完整 `load` 后才发布**会话，坏尾部、缺失文件仍进入启动问题报告，其它会话继续恢复。
- 严格的 `list_headers` / `scan_sessions` 语义不变。旧 JSONL 原字节不变，不生成旁路索引，不产生磁盘写入，也不要求手动迁移。
- 这一步减少启动时对全部 Journal 的重复读取/解析，**不减少磁盘占用，也不消除一次完整恢复所需的内存与 I/O**。

## 后续阶段的验收门禁

1. 为历史读取建立版本化的可丢弃索引或快照；以日志内容和 revision 校验，失配时退回原 JSONL 重放；恢复中断后不丢事件。
2. 旧批次压缩先采用**单文件原子替换**，避免“归档文件 + manifest + 活跃尾段”需要跨文件提交造成的崩溃窗口。v2 Header 允许普通 JSON batch 和 `batch_gzip` 混合；后续追加仍用普通 batch。显式 `compress_cold_session` 在会话锁下把旧完整批次压缩到同目录临时文件，校验完整 Session/Revision/审计读取后原子替换。未完成或不值得压缩时原文件不变；不会自动压缩活跃会话。
3. `request-audit` 对象的归档/清理必须从**全部**会话日志构建引用集；未知版本、损坏日志或无法读取的引用出现时停止清理，不能只凭文件年龄删除共享对象。
4. 新旧格式双读、迁移断点续跑、降级路径、跨平台文件锁与崩溃恢复都通过后，才能将磁盘回收作为默认行为。迁移前后用同一份真实历史测启动时间、峰值 RSS、磁盘实际块数与审计读取一致性。

第一阶段无须迁移；第二阶段只提供显式、逐会话迁移入口。尚未对已安装 App 的真实历史自动执行，因此不能提前宣传用户磁盘空间已下降。审计对象回收仍未实现。

## 第二阶段：显式冷 Journal 压缩

- 迁移入口：`JsonlSessionStore::compress_cold_session(id)`；单次只处理一个 ID。测试/维护二进制 `xharness-compact-journal --root <sessions-dir> --session <id>`，**先备份并选择闲置会话**，不对整个真实目录自动批量运行。
- 必须先升级所有会读取该状态目录的客户端，再迁移：新读端兼容 v1/v2，旧读端只认识 v1。需要降级时应先恢复迁移前备份；不能让旧版和新版同时写同一目录。
- v1 继续原样读写；v2 的压缩批次包含未压缩长度、未压缩 SHA-256、压缩 SHA-256 和 gzip/base64 数据。读时有 128 MiB 展开上限，校验后才反序列化；未知记录或损坏摘要失败关闭。只有单条批次至少 4 KiB 且压缩后节省超过 10% 才转成压缩批次。
- 迁移使用既有同会话进程锁及跨进程锁：原文件完整校验 → 临时文件写入并 sync → 临时文件完整重放并与原 Session 比较 → 文件指纹再次一致 → 原子替换并同步目录。崩溃前原文件不变，崩溃后只可能看到完整旧版或完整新版；临时残留不参与会话发现。
- 现阶段压缩会完整恢复一份会话进行验证，所以**大文件迁移的瞬时内存与 CPU 仍需实测**，不应自动对本机最大旧日志运行。它减少落盘字节，不等同于消除恢复时的完整重放。冷段索引/快照和自动空闲调度仍是后续任务。
