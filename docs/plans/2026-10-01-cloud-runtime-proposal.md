## 1. 核心决定与范围

让用户把一个明确授权的任务交给专用 Linux VM。VM 内运行完整 XHarness Host、Durable Runtime 和 Goal；本机负责提交、观察、回答问题、调整方向和停止。本机退出不终止已经接纳的远程任务。

采用 **VM 内 Full Access，VM 外保持隔离**。复用现有模型 Provider、工具注册、Loop、上下文预算、Compact、Goal 和 Session 持久化，不建立第二套 Agent 引擎。

第一条可交付路径是接入用户已有的专用 VM，完整实现任务生命周期和恢复。自动创建云主机作为后续环境适配器接入，不把特定云厂商放进 Core、Provider 或原生工具层。

本提案不包含：运行中的本地会话无缝迁移、任意 OS 进程快照恢复、外层评审模型、Kubernetes 集群、免费模型额度共享，以及跨 VM 副作用严格恰好一次执行的承诺。它也不授权创建真实 Goal、传输凭据、发布或替换当前软件。

## 2. 架构与职责

```text
Web / Tauri 客户端
  任务提交、远程会话、Steering、问题回答、停止
             │ HTTPS / WebSocket
             ▼

  用户身份与任务归属 ─────────────────→ 已有 VM / 云厂商 VM
  提交收据、环境绑定、生命周期          启动、探测、停止、磁盘绑定
  凭据引用、资源额度、事件接入                 │
             │ 认证连接                      │ 外部控制 VM
             ▼                              ▼
┌──────────────── 专用 VM 隔离边界 ─────────────────┐
│ VM 服务管理器 → xharness-host-app                 │
│                    │                             │
│ BasicHost → DurableLoopAgentRuntime               │
│                    │                             │
│ GoalController → DurableInbox → Driver → Core     │
│                                        │         │
│                          Provider / ToolRegistry │
│                                        │         │
│                          Linux 原生执行 FullAccess│
│                                                  │
│ 持久磁盘：工作区、Session、Control、附件、产物      │
└──────────────────────────────────────────────────┘
```

| 边界 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| 客户端连接层 | 本地或远程连接选择、事件恢复、用户操作反馈 | 决定 Goal 是否完成、维护远程执行队列 |
| 托管控制服务 | 任务归属、接纳收据、环境绑定、部署版本、生命周期、凭据授权、资源限制 | 根据模型输出另起续轮、复制 Goal 状态机 |
| 环境适配器 | 准备环境、启动与探测、停止、磁盘和产物保留 | 模型协议、工具参数、上下文策略 |
| VM 内 Host 与 Runtime | 用户输入、Goal、审批、问题、模型执行、工具调度、权威 Session | 云账号、VM 调度、其他租户权限 |
| 原生平台层 | VM 内文件、进程、网络能力和进程清理 | SSH 连接、云 API、跨机任务归属 |

控制服务不需要每步调用模型。Goal 决策和实际 Loop 都在 VM 内；控制服务断开时，已经启动的任务可按预先授权的策略继续。

环境注册必须探测并声明能力：外部停止 VM、持久卷、资源限制、可达的模型端点等。只有 SSH 访问的机器不能冒充具有云 API 级强制停止能力；缺失能力要明确标为不支持，不能把失败的停止操作记成成功。SSH 引导使用专用密钥和正常主机身份校验，不转发本机 SSH agent，也不把登录密钥传入模型上下文。

### 已有代码复用与真实缺口

- `crates/xharness-host-app/src/main.rs` 已组合模型配置、Session Store、Control Store、文件租约、工具、问题、Schedule 与 Durable Runtime；远程仍运行这套组合。
- `crates/xharness-host/src/runtime.rs` 的 `AgentRuntime` 是进程内能力接口，包含 Provider 对象和 Session 访问等方法。**不逐方法改成网络 RPC，也不为了远程部署将整个内部对象序列化。**
- `crates/xharness-agent/src/goal.rs` 的 GoalController 继续拥有自动推进、版本校验和持久提交；托管层只投影结果。
- `crates/xharness-api` 与 `xharness-server` 的现有会话接口用于远程会话操作；新增托管协议独立版本化，不随意改变上游兼容 RPC。
- 当前 `FileLeaseManager` 是本机跨进程锁，不是跨 VM 所有权协议；桌面 Token/Cookie 也是本机认证，不可直接作为公网多用户认证。
- 历史偏移索引和闲置恢复快照继续作为缓存使用，不因此升级为云端任务、工作区或进程的恢复真源。

## 3. 产品入口与工作范围

### 首选入口

在现有任务或会话菜单加入“托管到远程环境”，选择已配置的环境、目标、工作区来源、模型与权限，确认后进入远程会话。

该操作创建独立托管任务，不暗中移动当前本地任务。用户明确选择导入上下文时，只导入一致、可验证的历史切点；默认只提交当前目标和选定材料，避免把旧任务指令全部带入。

托管成功后仅增加必要表示：

- 会话显示“远程”、环境名称和连接状态。
- 复用现有 GoalBar 显示目标状态、问题、进展和控制。
- 连接丢失时显示“观察连接中断，远程任务可能仍在运行”，不得假报停止或完成。
- 运行状态、环境故障和结果分别显示，不再增加一套常驻诊断页面。

连接层需区分本机路径与 VM 路径。远程文件选择、附件和产物通过上传/下载与明确映射处理，不能把本机绝对路径当作 VM 文件。`host.openPath` 等本机交互能力必须有远程语义或明确禁用。Computer Use、桌面权限和其他平台专有工具按 VM 的真实 Probe 结果投影，不因本机可用就向远程模型宣称可用。

### 工具入口

点击入口与未来的模型委派入口应调用同一个托管应用服务。第一阶段不新增 `remote_bash`、`remote_read` 等工具；原工具在 VM 内原样工作。

若后续需要模型主动委派，可评审对现有 Agent 委派接口的扩展。工具只提交任务说明与已授权的环境、凭据引用，返回任务身份；模型不能提供任意云管理密钥、原始 API Key 或跨用户任务 ID 来获得权限。

系统提示词只说明当前执行环境、可用能力与路径，不负责切换执行位置。是否开启持久 Goal、是否把材料发往远程，均来自用户明确授权，不从普通聊天自动推断。

## 4. 托管契约

以下是拟议 DTO 与操作，不是当前已有接口。新增协议命名空间建议为 `xharness-cloud/v1`，与现有 `/api` 会话协议分离。

### 提交任务

```text
CloudTaskSpec
  request_id                     客户端重试使用的稳定接纳身份
  environment_ref                用户已授权的专用环境
  objective                      本次目标
  acceptance_criteria            用户条件；缺省时不自动追加要求
  workspace_source               Git revision / 上传包 / 已有远程工作区
  selected_context_refs          可选的历史切点或附件引用
  model_route                    Provider / API Base URL / Model / 配置引用
  credential_ref                 凭据引用，不是明文密钥
  permission                     显式 full-access
  system_privilege                普通用户 / 经确认的 sudo
  resource_policy                并发、CPU、内存、磁盘、运行时间限制
  usage_policy                   Token / 成本限制及缺失计量时的处理方式
  retention_policy               完成后环境、工作区与产物保留方式
  notification_policy            完成、失败、需要用户输入的通知
```

身份由认证上下文派生，客户端不能通过填写 `owner_id` 更换所有者。模型路由和上下文能力继续复用现有 Provider 配置，不在托管模块写死模型窗口或思考档位。

拟议操作：

- `task.submit / get / list`：接纳、查询和列出有权访问的任务。
- `task.open_session`：获取短期、任务限定的会话连接授权。
- `task.cancel`：停止后续推进并收敛当前执行，不等同于 Goal pause。
- `task.collect / release`：收集产物；按明确策略释放任务环境。
- `environment.register / inspect / prepare / stop`：管理已有 VM 或云端环境。

Steering、普通消息、问题回答、Goal 编辑/暂停/恢复与模型选择仍进入 VM 内原有 Host 接口。只有托管生命周期属于新增协议，不复制一套 Session 控制方法。

### 接纳与应用分开

1. 控制服务持久记录任务与 `request_id`，返回稳定 `task_id`。重试返回原收据，不创建第二台 VM 或第二个任务。
2. 环境分配、准备和启动是可重入的阶段，每阶段绑定同一任务与部署身份。
3. VM 端通过稳定的引导命令身份创建 Session、提交用户目标并启用 Goal；跨日志步骤逐项持久确认，崩溃后从未完成阶段恢复，不伪装成跨系统原子事务。
4. 返回 `accepted` 只表示持久接纳；实际开始需收到 VM 端的应用收据和运行投影。

同一个 `request_id` 配不同内容应拒绝为冲突。收据丢失后先查询，不另生成身份盲目重试。

## 5. VM 内 Full Access 与凭据

### 权限边界

Full Access 复用现有平台预设：不再用工作区级沙箱拦截已授权的 VM 内操作，仍保留受管进程、输出限制、取消和清理。它不意味着工具并发规则、文件观察校验或请求预算被关闭。

- 默认运行在专用用户下。安装系统依赖优先由环境准备阶段完成；任务确需 sudo 时显式选用相应环境配置。
- 即使授权 VM 内 root，也不授权宿主机、云管理平台或其他 VM；不能挂载宿主机 Docker socket、云管理凭据和无关用户目录。
- 任务运行凭据必须包含模型 Key 所需权限，但不自动包含 Git 推送、云部署或其他外部账号权限。VM 的文件权限不能约束已经获得 VM root 的任务，不能把它声称为另一层隔离。
- 启动、强制停止、资源限制和 VM 回收的最终控制在 VM 外，避免 Agent 改坏自己的服务后失去管理能力。
- 首次明确授予此环境 Full Access 后，不对范围内每次 Bash/Read/Write 重复审批；未授权的外部权限继续按原策略处理。

### 密钥传输

模型 API Host/Base URL 是配置；API Key 是凭据，二者分别处理。

1. 本机凭据通过独立的认证加密通道提交或引用，禁止混进任务描述、工具参数、导出对话和 URL。
2. 控制服务保存加密凭据或外部 Secret 引用，VM 只拿到任务所需项；云管理凭据留在控制服务。
3. 使用任务限定的短期引导身份，把 Key 注入 VM 的受限运行时配置或环境；不用原始 Key 作命令行参数，不在启动诊断中打印。
4. 提交、调试、请求审计和备份导出都要做密钥泄漏测试。默认只记录非敏感路由、配置版本和凭据引用。
5. 移除 VM 内副本不等于撤销第三方 Key。若供应商不支持临时 Key，轮换与撤销必须调用供应商机制或由用户执行，不能宣称任务结束后 Key 自动失效。

## 6. 状态与唯一权威

环境、托管任务和 Goal 是三个不同维度，不把它们揉成一个 `running`。

| 对象 | 拟议状态或投影 | 权威来源 |
| --- | --- | --- |
| 环境 | preparing / ready / degraded / stopping / stopped / failed | 控制服务与环境探测收据 |
| 托管任务 | accepted / provisioning / attached / settling / cancelled / finished / failed | 托管接纳、绑定和生命周期记录；settling 的 requested_outcome 区分完成、失败与取消 |
| Agent 与 Goal | running / waiting / paused / blocked / awaiting_confirmation / complete 等现有语义 | VM 内 Session 与 Control 持久记录 |
| 客户端连接 | connected / reconnecting / disconnected | 客户端连接层，仅表示观察状态 |

`attached` 只代表任务已绑定远程会话，不代表模型正在生成。模型报告完成也不直接把托管任务标成 `finished`；需要现有 Goal 验收结算，并确认没有未清理的受管执行。

控制服务保存 Goal 的可丢弃查询投影，不建立第二份可修改的 Goal 真源。投影须带来源 revision/seq 和观测时间；来源不可达时显示过期，不据此产生模型续轮。

### 不同停止操作

- **断开客户端**：仅断开观察，任务继续。
- **Goal pause**：沿用现有语义，停止后续自动轮次，不声称已杀当前工具。
- **停止当前轮**：走现有取消与进程收敛；保留会话和目标。
- **取消托管任务**：持久禁止后续任务推进，取消当前轮和受管任务，保存结算；未完成清理不能先报告 `cancelled`。
- **强制停止 VM**：最后的基础设施兜底。记录强制清理与未知工具结果，不能当成安全完成；已停止的进程无法通过 Session 日志恢复。

## 7. 持久化与恢复

### 必须保留的数据

- Session JSONL 及对象引用、Control 日志、收件箱、Goal、问题、审批和命令收据。
- 工作区文件与未提交修改、附件、测试结果和指定产物。
- 部署版本、协议版本、磁盘绑定和恢复状态。

工作区与状态保存在任务绑定的持久卷；可丢弃缓存、构建缓存与有界诊断独立存放。控制服务数据库保留接纳及环境归属，但不每轮复制整份上下文。后续备份可复用现有内容寻址对象，不在提案中指定新的全量重复审计格式。

释放环境与删除数据是不同操作。默认释放 VM 不删除保留的对话、工作区和产物；执行保留期清理或永久删除时需明确范围与用户授权。重新分配给其他用户前必须完成环境及任务凭据清理，不把旧磁盘直接转交。

JSONL 与工作区不是天然原子快照。导出或迁移必须先达到执行静止点，再生成带 revision、文件清单和 Hash 的一致恢复包；运行中拿两份独立备份不能声称它们来自同一切点。

### 故障分类

| 故障 | 恢复方式 |
| --- | --- |
| 本机睡眠、断网、WebSocket 重连 | 重连远程 Host，补持久事件；不新建 Goal，不取消执行 |
| 控制服务重启 | 从持久接纳/绑定恢复，核对已有 VM 和启动收据；不另建重复任务 |
| VM 内 Host 崩溃 | 同盘重启，复用现有恢复；未执行输入可恢复，在飞副作用沿用 `outcome_unknown` 保护 |
| VM 重启 | 恢复文件和 Session；Job/PTY 原进程已消失，不能当成成功或自动重建 |
| VM 丢失、持久磁盘仍在 | 先确认旧执行环境已失去执行能力，再绑定磁盘到新 VM；未知副作用需要验证或用户处理 |
| 磁盘损坏、丢失或空间耗尽 | 显式失败/停止新执行；只从已验证备份恢复，不能伪报无损 |
| 模型或必要服务暂时不可达 | 复用原 Provider 重试语义；已输出内容和副作用不由托管层重新播放 |

第一阶段不做依据“心跳超时”自动跨 VM 抢任务。单台专用 VM 的排他绑定、磁盘单写者约束和本机文件租约共同防止重复接管；跨 VM 切换必须外部停止旧 VM 并确认排他性。

未来自动故障转移需要单独实现所有权 epoch 与 fencing：拒绝旧实例控制/写入，并阻止旧 VM 继续执行。只增加分布式锁或把 epoch 放进日志，不能阻止已运行的旧 Bash 产生外部副作用，因此仍不承诺外部操作恰好一次。

## 8. 长期推进与远程交互

复用现有 GoalController，不新增定时发送“继续”的脚本：

- 可推进时沿用原 Inbox、Driver 和验收路径。
- 等待必要 Job、子 Agent 或时间事件时，用事件/持久 Schedule 唤醒，不空转调用模型。
- 用户提问沿用当前软等待与迟到回答机制；不因为托管引入新的自动答题规则。
- 等待审批时保留请求并通知用户；Full Access 不能替用户批准未授权的外部账号操作。
- 用户的新范围通过现有 Steering 进入持久收件箱；客户端展示“已接纳”和“已应用”的区别。
- 本机关闭时通知只能走已配置且受支持的渠道；没有渠道则保留待办，重连可见，不假称已通知。

资源/Token 限制是用户授权和环境容量，不是新加一个固定 Goal 轮数上限。资源不足应给出具体原因。费用缺失时不能把未知 Usage 当零或伪造实测 Token；硬成本控制需要模型供应商额度或专门的计费网关支持。

等待期间默认保留 VM，保证必要 Job 不被破坏。只有确认没有运行 Job、问题/审批恢复材料已落盘、恢复能力满足条件后，才允许显式休眠或回收；持久磁盘继续计费也应在 UI 中说明。

### 连接与事件恢复

公网接入使用 TLS、任务归属校验和短期会话授权；桌面本机 Token 不暴露为公网管理凭据。VM Host 不裸露到公网，优先由控制服务的认证 Gateway 访问；需要出站通道时由连接适配器替换，不改变 Loop。

远程会话复用原 API 的请求和事件结构，但需要验收其断线恢复能力，不能把现有字段存在等同于已经可靠：

- 以持久 Session seq/revision 做恢复边界；托管管理事件使用自己的 cursor，两者不混用。
- 流式临时 Delta 不是持久确认，不能逐 chunk 假造恢复 cursor。重连用权威投影校准显示，并避免把已显示内容再追加一次。
- cursor 太旧或缓存被淘汰时，返回显式重新同步信号，重取历史/状态；不能静默丢事件。
- 用户命令重发沿用稳定身份和原幂等路径。收到回执前断线属于“确认未知”，不是未执行。
- WS 断开、关闭页面和 Gateway 超时都不得自动调用任务取消。取消必须是独立持久命令。
- 客户端慢消费、反复重连和多个观察者不能拖住 Agent 执行，也不能导致无界内存队列。

## 9. 渐进实施与回归门禁

| 阶段 | 实现内容 | 完成门禁 |
| --- | --- | --- |
| 1 固定契约 | 托管 DTO、接纳身份、环境能力、独立状态机、错误分类；Fake 环境适配器 | 状态迁移、重复提交、阶段崩溃、归属拒绝、版本兼容测试通过 |
| 2 接入专用 VM | 已有 VM 适配、完整 Host 启动、模型凭据注入、工作区准备、持久磁盘、认证 Gateway | 本机关掉后仍推进；重连、回答、Steering、取消均走真实 Host；无明文 Key 泄漏 |
| 3 恢复与运维 | 引导幂等、Host/VM 重启恢复、排他接管、清理、额度、保留与通知 | 下面的故障矩阵及真实 Goal 验收通过，错误不误标完成 |
| 4 自动环境 | 云 VM 创建/回收适配器、环境模板、版本固定、选定备份恢复 | 超时后核对资源而非重复创建；删除目标准确；恢复包验证；成本/保留状态可见 |

阶段 2 和 3 验收后，“接入用户自己的 VM”就是完整受支持的产品路径，不需要等待自动购置云主机。自动故障转移、多租户调度池和运行中迁移另行立项，不隐藏在基础托管交付里。

实施时新建托管应用服务与环境适配边界；不在 `BasicHost` 或 RPC 分发文件增加云厂商状态，不让 `xharness-core` 依赖云 SDK。具体 crate 数量在契约阶段确定，不为了抽象先堆空壳模块。

### 离线与故障测试

1. 同身份重复提交、内容冲突、收据丢失、VM 创建成功但控制服务未收到响应。
2. 在持久接纳、环境绑定、Session 创建、目标输入、Goal 启用前后分别杀进程；恢复不重复输入或启用。
3. 本机退出、网络切换、Gateway 重启、慢观察者、多客户端并发观察；任务不受误取消影响。
4. 用户消息/Steering 与 Goal 续轮竞争；模型按新范围前进，旧报告不能结算新目标。
5. 问题软等待、迟到回答、审批过期、重复回答与跨用户响应；恢复状态与 UI 一致。
6. 正常取消、清理超时、后台后代进程、VM 强制停止；不得残留未说明的执行或伪报安全取消。
7. Host panic、VM 重启、旧实例仍存活、磁盘双挂载尝试；排他性不足时禁止接管。
8. 工具已有 Call 无 Result、外部操作已经成功但回执丢失；不能自动重放非幂等操作。
9. 磁盘满、对象缺失、坏恢复包、持久日志损坏；缓存失败可回退，真源损坏不可当空历史。
10. 凭据过期、撤销、错路由、DNS/TLS 失败、无 Usage；分类准确且无密钥输出。
11. 运行中更新、协议/存储版本不兼容、过期客户端；默认固定任务版本，先静止再维护，禁止自动降级写同一目录。
12. 工作区路径穿越、上传包符号链接、未提交修改遗漏、运行中导出、多个任务同时写同一目录。

### 真实模型验收

Rust 编译与基础回归默认在 `WZU_Server` 执行，真实 DeepSeek 编程回归先使用隔离测试工作区，不开放共享服务器的系统修改权限。完整 VM 边界、Full Access 和外部强制停止验收必须在用户指定的专用测试 VM 上进行；不能把“服务器上另建一个目录”当成 VM 隔离。机器不可达则报告阻塞，不回退到 Mac，不干扰现有桌面、Web 或模型服务。

验收必须覆盖多轮工具与 Goal 推进、后台 Job、一次用户改范围、一次问题回答、本机观察断线、Host 恢复和终态清理。中断注入在可控测试工作区执行；真实外部副作用不作为自动重放测试目标。成果由独立脚本运行测试并核对文件，不只接受模型“已完成”的正文。

先运行确定性的 Fake Provider/环境故障矩阵，再运行真实模型，记录源码 SHA、环境/协议版本、输入身份、Session revision、关键收据、资源峰值与耗时。这里没有运行过测试，不能填写通过数或宣称已验证。

## 10. 主要代价与待确认项

- VM 开着和持久磁盘保留会产生基础设施成本；暂停 Goal 不代表 VM 停机。
- Full Access 降低工作区级审批阻力，但模型仍可能改坏 VM 环境，需要模板、恢复材料和外部停止能力。
- 本机不再是远程任务执行真源，离线观察缓存不能被当成可写历史。
- 第一阶段推荐一项任务独占一台专用 VM；个人 VM 复用与多任务共享需要显式冲突和清理策略。不同用户不共享同一个 Full Access 环境。
- 单机恢复可以复用现有持久能力，但无损 VM 灾难恢复和跨机自动接管需要额外验证，不由“已有 Goal”自动获得。

建议确认：先以专用 Linux VM、点击托管入口、VM 内 Full Access、持久磁盘、原 Goal 验收作为第一条支持路径；模型工具委派和自动创建云主机随后接入相同契约。

## 11. 参考与区别

- [OpenHands Remote Agent Server](https://docs.openhands.dev/sdk/guides/agent-server/overview)：Agent Server 可部署到 VM 等基础设施，客户端通过 HTTP/WebSocket 访问，复用本地/远程 Agent API。本提案借鉴完整执行端远程部署，不复制其存储或 SDK。
- [Claude Code 自托管环境](https://code.claude.com/docs/en/self-hosted-environments)：控制面分派任务，Runner 在自有环境启动会话。本提案借鉴任务与环境职责分离，但自持 XHarness 控制和 Runtime，模型 Provider 不绑定厂商。

以上参考支持分层选择，不证明本提案的恢复、权限或性能已经实现。
